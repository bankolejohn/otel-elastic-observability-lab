# Drill 4 — slow (silent fault, second run)

**Date:** 2026-11-11. **Injected:** 14:29:24Z, ~4 minutes. **Actual fault:** `slow` (inventory-service `pg_sleep(2)` on every stock query). The drill was a random pick, not forced.

## Result

**Not scored for root-cause correctness.** The responder recorded alert evidence but never committed a one-sentence diagnosis or a T2 before the answer was revealed. The reveal was requested to wrap up. The drill is therefore recorded as *detection exercised, diagnosis not completed*. This is a result, not a failure of the system: it was a partial run of the drill procedure.

## Detection (from the alert emails, Kibana local time = UTC+1)

| Time (local) | Alert | Meaning |
|---|---|---|
| 3:29 PM (14:29Z) | Latency SLO | **T1.** About one minute after injection. |
| 3:30 PM | DB pool saturated | Slow queries hold connections longer, so the pool (size 5) fills. |
| 3:31 PM | ML request-volume anomaly | Request pattern shifted (inventory-service flagged ~60x). |

The error-volume rule stayed silent, correctly: there were no errors. The 3:17 PM error-volume email the responder also received came from an earlier validation burst (12 deliberate failures at 14:16Z), not from this drill.

## Evidence (queried afterwards)

| Window | Orders | p50 | p95 | 5xx |
|---|---|---|---|---|
| Healthy 14:20-14:28Z | 20 | 94 ms | 164 ms | n/a |
| Drill 14:29-14:35Z | 495 | 2,188 ms | 4,150 ms | 0 |

`logs.obs-shop.errors*` had 0 documents in the drill window. Every order succeeded, but typical latency was about 23x baseline. This is the same signature as drill 3: a fault invisible to an error-rate alert and visible only to latency.

## What the signals pointed to

Latency up with zero errors rules out `query_timeout` (8 s sleep, would cross the 5 s client timeout and produce 5xx), `connection_failed` (errors) and, with p50 near 2.2 s, the 4 s `pool_exhausted` hold (which times out at 3 s and produces errors). A steady ~2 s added to every request with no failures matches `slow`. Pool saturation is a *consequence* (queries held longer), not the cause.

## Timeline gaps

- T2 (root cause) was never recorded.
- The responder's first queries returned 0 rows because the Discover time picker intersects with the query's `WHERE`; it was set to a recent window that excluded the drill. See `docs/esql-cheatsheet.md` gotchas.

## What would have been faster / action items

1. **Alert text is generic** ("Document count is 1"). Include service, p95 and threshold in the message so the email alone points at latency vs errors.
2. **Alert-to-cause hint:** a latency alert plus a pool-saturation alert plus a silent error rule is the signature of `slow`. Add this triage table to the runbook.
3. **Document the time-picker trap** (done in the cheatsheet).
4. **Make the postmortem step mandatory before reveal:** a drill without a committed diagnosis teaches detection but not diagnosis.

## Lessons

- All three relevant alerts fired within two minutes without anyone watching a dashboard, which is the point of the alerting work.
- The earlier validation burst can be mistaken for drill signal. Note validation activity in the incident log so it isn't confused with drill alerts.
